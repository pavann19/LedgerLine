# Security

Both services run as stateless OAuth2 resource servers. `local-jwt` mode validates HS256 signatures with a required secret of at least 32 bytes; every secret holder can mint OPERATOR tokens. `oauth2` mode validates RS256 tokens against a configured provider, requires the expected issuer and audience, and never falls back to the local secret. Both modes require a nonblank `sub` without the internal key separator and an `exp` claim; timestamps are validated with Spring Security's default clock skew. API access requires a CUSTOMER or OPERATOR role. Provider URLs require HTTPS, with loopback HTTP allowed for local tests. See [authentication, OpenAPI and rate-limit setup](API_SECURITY.md).

CUSTOMER can create customer accounts, read owned accounts/postings, and debit owned accounts. OPERATOR can provision OVERDRAFT/INTERNAL accounts and access all accounts. Destinations need not belong to the sender. No account enumeration, historical mutation, admin login, closure, or debug endpoint exists.

Projection customers require the account UUID in the signed accounts claim. The projection service does not query current ledger ownership. Token issuers must supply correct short-lived claims; ownership reassignment/revocation is unsupported. Operators bypass claim checks.

Health, OpenAPI and Swagger UI are public. OpenAPI declares bearer authentication, optional OAuth2 authorization-code flow with Swagger PKCE, and API error/429 contracts. All other paths default to denied, including metrics despite actuator exposure configuration. Prometheus needs an explicit authenticated operational integration before successful scraping is claimed.

Controller calls derive identity and role from the security context. Trusted internal service overloads use SYSTEM/legacy scope for fixtures and experiments and are not exposed as HTTP endpoints. Do not expose them through another transport without authorization.

SQL administrators and Kafka producers are trusted. Local Compose uses the PostgreSQL owner and plaintext Kafka. UPDATE/DELETE triggers protect postings, transaction headers, and audit records; owners can disable triggers, TRUNCATE, or change balances directly. No tamper-evident audit chain or request correlation ID exists.

Pagination is bounded to 100 rows. Per-subject token-bucket rate limits are enabled on authorized API requests, with bounded in-memory identity state, 429 Problem Details and Retry-After. Limits apply separately to each service process and reset on restart; they are not a shared quota across replicas or protection against unauthenticated traffic. Request-size limits beyond Tomcat defaults, TLS termination, payment callbacks and signing-secret rotation are unsupported. Compose binds host ports to localhost and contains local-only PostgreSQL/Grafana credentials. AWS examples require a reviewer CIDR but still expose HTTP and place secrets in Terraform state/user data. Shell tracing is disabled; this is not a secret-manager implementation. Production and real-money deployment are unverified.

Java target 21 and Maven 3.9.9 are pinned. Dependency versions come from the Boot BOM plus explicit overrides. Actions use resolved Git SHAs; default permissions are contents:read. Raw Trivy HIGH/CRITICAL findings remain visible. A separate blocking gate rejects actionable findings. Spring Boot 4.0.9 manages Spring Framework 7.0.10, which patches the two previously reviewed Spring MVC vulnerabilities. The applicability policy now contains zero active exceptions; MVC regression receipts remain defense-in-depth evidence. See ../security/README.md. Mutable image tags, apk upgrade inputs, and wrapper archive integrity limit full reproducibility. Dependency upgrades alone do not prove a clean image scan.

Report vulnerabilities privately to the repository owner through GitHub; do not post tokens, signing secrets, or financial data publicly.

Identity-provider login, user registration, consent, refresh tokens and revocation remain the provider's responsibility. External provider deployment and browser sign-in are not validated by the local JWKS tests. RS256 public-key refresh for a new key ID is exercised by the HTTP regression suite; immediate revocation of already cached keys/tokens is not guaranteed.
